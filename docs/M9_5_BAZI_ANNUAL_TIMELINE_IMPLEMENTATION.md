# M9-5 八字流年确定性时间轴实施说明

## 1. 阶段目标

M9-5 在 M9-4 大运排期之上建立可版本化、可回放的流年时间轴。程序只回答以下确定性问题：

- 某个流年的干支是什么；
- 该流年从哪一刻立春开始，到下一年立春前结束；
- 出生流年的有效区间从何时开始；
- 该流年实际落在哪一步大运；
- 若交运发生在流年内部，交运前后分别属于什么时间阶段。

本阶段不输出流年吉凶、旺衰作用、喜忌变化或具体事件预测。

## 2. 核心口径

### 2.1 以精确立春切换流年

流年不按公历 1 月 1 日切换，而采用：

```text
流年 Y = [Y 年精确立春时刻，Y+1 年精确立春时刻)
```

区间使用前闭后开语义，处于下一年立春时刻的瞬间已经进入新流年，避免边界时刻同时属于两个年份。

`lunar-javascript` 提供的精确年干支和节气表用于生成边界。项目固定依赖版本后，将方法版本、引擎版本和计算结果一起保存。

### 2.2 流年与大运按实际区间求交集

不能仅按公历年份或名义年龄把整个流年归入某一步大运。系统对流年有效区间和每步大运区间求交集：

```text
流年有效区间 ∩ 大运区间 = 本流年中的大运片段
```

例如首运在 `2030-12-12 06:51:00` 开始，则 2030 庚戌流年会被拆为：

1. 2030 年立春至交运前：交入首运前；
2. 交运时刻至 2031 年立春前：第一步大运。

后续两步大运的交接若位于流年内部，也会拆成前后两段，不把整年强行归到某一运。

### 2.3 出生与末运边界裁剪

- 首个流年从命盘年柱反推，兼容公历年初、立春前出生的情况；
- 出生流年的有效开始时刻取“立春”和“出生时刻”中的较晚者；
- 完整排期的末个流年按第八步大运结束时刻裁剪；
- 未知时辰或大运精确边界未建立时，仍生成 81 个立春流年，但不生成大运归属；
- 非 `Asia/Shanghai` 时区在 v1 中只生成干支顺序，不伪造精确立春时刻。

## 3. 状态与能力边界

### `complete`

- 流年干支可用；
- 精确立春边界可用；
- 流年和大运的实际交集可用。

### `annual_schedule_only`

- 流年干支和精确立春边界可用；
- 因未知时辰等原因，大运交接时刻不可用；
- 不生成大运归属。

### `sequence_only_unsupported_timezone`

- 只提供流年干支顺序；
- 不提供精确立春时刻或大运归属。

任何状态都明确关闭：

- `annualInterpretation`；
- `eventPrediction`。

## 4. 数据结构

### 4.1 年度条目

每个 `BaziAnnualTimelineItem` 保存：

- 公历标识年和流年干支；
- 本年、次年立春时刻；
- 经出生和末运裁剪后的有效区间；
- 是否从出生前开始；
- 实际大运片段数组；
- 是否跨越交运边界；
- 当前排期状态。

### 4.2 大运片段

每个 `BaziAnnualLuckSegment` 保存：

- 片段开始和结束时刻；
- `pre_luck` 或 `luck_cycle` 类型；
- 大运序号和干支；
- 可直接展示的事实标签。

时间片段保留秒级边界，不用名义年份代替真实交运时刻。

## 5. SQLite v27 持久化

新增 `bazi_annual_timeline_versions`：

- 绑定命盘版本和大运排期版本；
- 保存方法版本、引擎版本；
- 保存命盘、大运和流年时间轴三层指纹；
- 保存完整结果 JSON；
- 相同命盘、大运、方法和引擎复用同一版本。

`bazi_conversations` 新增 `annual_timeline_version_id`。新会话会绑定 M9-5 版本，旧会话在读取时自动补齐，并升级到提示词版本 `bazi-chat-annual-timeline-v4`。

## 6. 接口与页面

新增接口：

```text
GET  /api/bazi/charts/:id/annual-timeline
POST /api/bazi/charts/:id/annual-timeline
```

排盘页新增“流年确定性时间轴”面板：

- 可选择、前后切换流年；
- 显示流年干支和精确立春区间；
- 显示实际大运归属片段；
- 跨运流年显示醒目标记和前后两个片段；
- 未知时辰或未校准时区显示明确降级状态。

## 7. 对话上下文

八字上下文新增版本化流年快照，但不会把完整八九十年数据无差别塞给模型：

1. 从当前问题提取范围内的四位年份；
2. 若提取成功，注入该年及前后各两年；
3. 未指定年份时，注入当前年份及前后各两年；
4. 无论聚焦哪一年，额外注入全部跨运流年，避免遗漏真实交运边界；
5. 清单只包含排期事实，不包含流年解释。

能力清单新增 `annual_timeline_schedule`，同时明确禁止 `annual_interpretation`、`annual_prediction` 和 `event_prediction`。

## 8. 校验覆盖

自动化测试覆盖：

- 方法配置完整性；
- 2022、2023 年精确立春时刻和年干支；
- 出生流年有效起点裁剪；
- 2030 年首运交接的前运前／第一运双片段；
- 2040 年第一运／第二运双片段；
- 未知时辰降级；
- 未校准时区降级；
- SQLite v27 迁移、去重和级联关系；
- 会话绑定、按问题聚焦年份和输出越权检查；
- TypeScript、生产构建和桌面／移动端页面验收。

## 9. 来源与限制

- [6tail 阴历干支文档](https://6tail.cn/calendar/lunar.ganzhi.html)：精确年干支以立春交接时刻为界；
- [6tail lunar 官方实现](https://github.com/6tail/lunar-java/blob/master/src/main/java/com/nlf/calendar/Solar.java)：节气及精确时间实现的交叉校验；
- [《三命通会》总论岁运](https://www.shiwens.cn/bookv_13526.html)：仅用于确认流年太岁和大运的分层概念，不将古籍吉凶断语写入算法。

历法实现能提供确定性时间边界，但传统命理解释不属于可科学验证的因果模型。本项目必须持续区分“排期事实”“规则证据”和“解释边界”。
