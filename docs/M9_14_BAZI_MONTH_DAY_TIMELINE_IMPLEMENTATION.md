# M9-14 八字流月、流日确定性时间轴实施说明

## 1. 阶段结论

M9-14 在 M9-5 的流年—大运时间轴之下补齐流月、流日事实层。系统现在可以针对某一个已保存流年生成并缓存：

- 十二个按精确“节”交接的流月区间；
- 继承原命盘晚子时口径的流日区间；
- 流月与流年有效区间的交集；
- 流月、流日与大运片段的时间交集；
- 同一流日内部跨越节界或交运时刻时的多个可审计片段。

本阶段只回答“何时开始、何时结束、当时属于哪个流月与大运”，不回答吉凶、旺衰变化和现实事件。

## 2. 为什么不按公历月初切流月

八字流月不是公历自然月。本实现采用精确节界：

| 流月序号 | 起始节 | 地支 |
| --- | --- | --- |
| 1 | 立春 | 寅 |
| 2 | 惊蛰 | 卯 |
| 3 | 清明 | 辰 |
| 4 | 立夏 | 巳 |
| 5 | 芒种 | 午 |
| 6 | 小暑 | 未 |
| 7 | 立秋 | 申 |
| 8 | 白露 | 酉 |
| 9 | 寒露 | 戌 |
| 10 | 立冬 | 亥 |
| 11 | 大雪 | 子 |
| 12 | 小寒 | 丑 |

每个流月使用前闭后开的 `[本节精确时刻, 下一个节精确时刻)` 区间。例如 2030 年卯月不是从 3 月 1 日开始，而是从惊蛰 `2030-03-05 21:03:18` 开始。

历法实现使用 `lunar-javascript` 的节气表与 `getMonthInGanZhiExact()`。官方文档将该接口定义为按精确节交接的月干支：[6tail 干支文档](https://6tail.cn/calendar/lunar.ganzhi.html)、[lunar-javascript](https://github.com/6tail/lunar-javascript)。

## 3. 流日换日规则

流日不新增独立流派开关，而是继承命盘版本已经保存的 `lateZiPolicy`，保证基础盘与动态时间轴不出现两套口径。

### 3.1 `same_day`

- 23:00—23:59 仍算民用当天；
- 一个流日区间为 `[当天 00:00, 次日 00:00)`；
- 日干支采用 `getDayInGanZhiExact2()`。

### 3.2 `next_day`

- 23:00 起算次日；
- 有效日期 D 的流日区间为 `[D 前一日 23:00, D 当日 23:00)`；
- 日干支采用 `getDayInGanZhiExact()`。

这两种口径与 M9-0 基础排盘使用的 `EightChar.setSect(2/1)` 保持一致。

## 4. 跨边界流日为何必须拆段

节界和交运时刻可能发生在一天中间。如果只给每一天保存一个“所属流月”或“所属大运”，就会丢失真实边界。

例如 2030 年 3 月 5 日采用 `same_day` 时：

```text
2030-03-05 00:00:00 — 21:03:18  戊寅流月
2030-03-05 21:03:18 — 24:00:00  己卯流月
```

2030 年 12 月 12 日又在 `06:51:00` 发生交运，因此同一个流日会保留“交入首运前”和“第 1 步大运”两个片段。界面和 AI 快照都按片段解释，不能把整天强行归到一侧。

## 5. 数据模型与按年缓存

SQLite 升级到 v36，新增 `bazi_month_day_timeline_versions`：

- `chart_version_id`：绑定不可变命盘版本；
- `annual_timeline_version_id`：绑定 M9-5 流年时间轴版本；
- `target_year`：本版本只保存一个目标流年；
- 方法版本、引擎版本和上游指纹；
- 12 个流月、约 365—367 个有效流日及其分段；
- 本结果指纹与完整 JSON 快照。

唯一键由命盘、流年时间轴、目标年份、方法版本和引擎版本组成。相同输入重复请求会复用旧版本。

没有一次性保存八九十年全部流日。一个命盘全生命周期可能产生三万条以上流日记录，既浪费 SQLite 空间，也会拖慢序列化。现在采用“用户切换到某个流年时按需生成并缓存”的粒度：

```text
命盘版本
  └─ M9-5 流年时间轴版本
       ├─ 2026 流月流日版本
       ├─ 2030 流月流日版本
       └─ 其他年份按需生成
```

`bazi_conversations.month_day_timeline_version_id` 固定绑定默认年份版本；如果用户问题明确包含另一个合法年份，上下文构建器会按需读取或生成该年份版本，并把实际版本 ID 和指纹写入本次上下文清单。

## 6. API

新增：

- `POST /api/bazi/charts/:id/month-day-timeline`：传入 `targetYear`，生成或复用该年版本；省略时使用当前可用年份。
- `GET /api/bazi/charts/:id/month-day-timeline?year=2030`：读取该命盘指定年份的最新版本，同时返回已生成版本列表。

年份必须是整数并落在 M9-5 流年范围内。越界请求直接拒绝，不偷偷扩大上游范围。

## 7. 工作台交互

八字排盘工作台在流年面板下新增“M9-14 流月流日确定性时间轴”：

- 与上方流年选择器联动；
- 十二流月卡片显示干支、起始节和精确起止；
- 月内跨运时显示提示；
- 流日核验器可选择具体日期；
- 流日卡显示干支、换日区间和全部时间片段；
- 当天跨节或跨运时明确解释为何存在多个片段。

已保存命盘切换年份后会在后台缓存对应年份版本；单次未保存排盘仍可在浏览器内确定性计算，但不会写入数据库。

## 8. AI 上下文与边界

提示词升级为 `bazi-chat-month-day-timeline-v13`。

上下文新增“权威八字流月流日确定性时间轴快照”：

- 用户问题包含年份时，路由到该年份版本；
- 包含 `YYYY-MM-DD`、`YYYY年M月D日` 或 `M月D日` 时，只展开该流日；
- 未指定日期时注入十二流月及少量跨边界流日，不注入全年数百条日记录；
- 上下文清单记录实际使用的版本 ID、目标年份和指纹。

新增允许能力：

- `month_day_timeline_schedule`

新增禁止能力：

- `month_day_interpretation`

输出守卫新增“越权解释流月流日吉凶”。模型可以解释节界、换日和时间归属，不能把某流月或流日直接改写成发财、破财、婚恋、疾病或事业事件。

## 9. 时区降级

v1 精确时刻继续只承诺 `Asia/Shanghai`。其他时区不会伪造绝对节界：

- 保留十二流月干支顺序；
- 不生成精确节界；
- 不生成流日；
- 不生成大运时间交集；
- 状态标记为 `sequence_only_unsupported_timezone`。

## 10. 测试覆盖

专项测试 `test:bazi-month-day-timeline` 覆盖：

- 方法契约校验；
- 立春、惊蛰等精确节界；
- 十二流月干支序列；
- `same_day` 与 `next_day` 两种流日区间；
- 同一天跨节界的分段；
- 同一天跨交运时刻的分段；
- 非支持时区安全降级；
- SQLite v36 迁移、版本指纹和相同年份复用；
- API 按年份生成；
- 会话默认绑定、问题年份动态路由和上下文清单；
- 流月流日越权吉凶输出守卫。

## 11. 当前不能回答的问题

M9-14 完成后仍不能自动回答：

- 某个流月或流日是吉是凶；
- 流月、流日进入后日主变强还是变弱；
- 某一天是否适合投资、结婚、就医、辞职或做重大决定；
- 流月、流日干支与原局、大运、流年关系的最终作用结果；
- 某个时间点必然发生什么事件。

## 12. 下一阶段：M9-15

建议在已完成的精确时间事实层上建立“流月、流日动态关系证据审计”。下一版可以按用户指定日期按需组合原局、大运、流年、流月、流日，复用 M9-6 至 M9-11 的关系、条件、十神、显隐与触达规则，输出可追溯证据；仍不计算吉凶分数，也不预测具体事件。完成这一层后，再进入人生事件智能提取与用户确认。
