# M1-2 紫微流月确定性排盘第一版实现说明

## 1. 本阶段完成内容

M1-2 在既有年度运限之上增加紫微流月事实层。用户可以在时间运势页切换“年度分析 / 流月分析”，选择任意公历观察日，系统会确定该日所属的农历流月，并展示：

- 流月的公历有效起止日期；
- 当前流年、大限和虚岁背景；
- 流月干支、流月命宫；
- 流年四化背景与流月四化；
- 流月十二宫映射和流曜落宫；
- 流月命宫三方四正及四化落宫形成的重点宫位；
- 每一项事实的计算来源和边界说明；
- 可直接用于当前流月追问的 AI 上下文。

本阶段只把确定性排盘事实、缓存和上下文链路做完整，不新增“AI 猜月份”的提示词模拟，也不生成必然事件或绝对吉凶。

## 2. 历法与流派边界

### 2.1 为什么页面选择的是公历日期

一个公历自然月通常会跨越两个农历月。如果界面只让用户选择“2026 年 3 月”，系统无法唯一判断用户要看农历正月还是二月。因此页面使用“公历观察日”，再由程序映射到唯一的农历流月。

例如当前固定案例：

| 观察日 | 归属流月 | 流月有效范围 |
| --- | --- | --- |
| 2026-03-18 | 2026 年正月 | 2026-02-17 至 2026-03-18 |
| 2026-03-19 | 2026 年二月 | 2026-03-19 至 2026-04-16 |

### 2.2 本版本采用的换月规则

本模块明确采用 `iztro 2.5.8` 默认的 `normal` 运限边界：流月按农历初一换月。快照通过 `boundaryPolicy: lunar-month-first-day` 固化该口径，避免未来规则升级后把不同口径的数据混在一起。

紫微流月口径和项目里的八字流月不是同一规则：

- 紫微 M1-2：按农历初一换月；
- 八字 M9-14：按节气中的“节”精确换月。

两套引擎、版本号、快照和上下文完全分离，不能相互套用。

## 3. 确定性计算链路

```text
公历观察日
  → lunar-javascript 定位农历年、月、日
  → 回推本农历月初一并寻找下一个初一
  → 得到唯一流月起止区间
  → iztro horoscope 计算大限 / 流年 / 流月
  → 对齐本命十二宫、四化与流曜
  → 生成 MonthlyTransitSnapshot
  → 按“会话 + month + 月初日期 + 引擎版本”缓存
```

快照统一以流月起始日作为 `targetDate` 和 `representativeDate`。因此用户在同一农历月内选择不同日期，得到的是完全相同的快照和同一条 SQLite 记录；只有跨过农历初一才会生成下一条记录。

流月引擎独立使用版本号：

```text
transit-month-v1-iztro-2.5.8-normal-lunar-boundary
```

年度引擎版本保持不变，避免本次功能升级造成历史年度报告无意义地重新生成。

## 4. 数据结构

`MonthlyTransitSnapshot` 的关键字段如下：

| 字段 | 作用 |
| --- | --- |
| `lunarMonth` | 农历年、月、是否闰月、名称、公历起止和天数 |
| `year` | 观察流月所在的流年干支 |
| `decadal` | 所在大限及本命落宫 |
| `flowYear` | 流年命宫事实 |
| `flowMonth` | 流月命宫、干支与本命落宫 |
| `yearlyTransformations` | 流年四化背景 |
| `transformations` | 流月四化及本命落宫 |
| `palaceMappings` | 流月十二宫名称和流曜与本命宫逐宫对齐 |
| `keyPalaces` | 流月命宫三方四正、四化落宫形成的重点宫位 |
| `topicPalaces` | 事业、关系、财务和健康对应的流月宫位 |
| `evidence` | 换月、干支、命宫、四化、流曜和十二宫映射依据 |

数据库不需要增加新表。原 `transit_snapshots` 已预留 `year / month / day` 层级，本次将快照类型扩展为年度与流月联合类型，并继续使用原有唯一键和会话级联删除。

## 5. 接口与页面

### 5.1 运限接口

```http
GET /api/conversations/:id/transits?level=month&date=2026-03-18
```

约束：

- `date` 必须是实际存在的 `YYYY-MM-DD` 日期；
- 日期不能早于出生日期；
- 最远不超过出生年后 130 年，并受 2200 年上限保护；
- 返回记录的 `targetDate` 是所属流月的月初，不是任意观察日。

### 5.2 时间运势页

页面新增“年度分析 / 流月分析”切换。流月模式提供：

- 观察日期选择；
- 上一流月、下一流月快捷导航；
- 观察日到农历流月的明确归属说明；
- 流年背景、流月四化、重点宫位、流曜和计算证据；
- 保留年度流年盘面作为上层背景，流月事实在下方独立呈现。

年度总结报告只在年度模式出现。本阶段没有把年度报告错误复用于流月，也没有自动生成月报。

## 6. AI 上下文

用户在流月模式发问时，消息元数据保存：

```json
{
  "transit": {
    "level": "month",
    "targetDate": "2026-02-17"
  }
}
```

Context Builder 会重新从数据库读取或计算该流月快照，再注入 L2.5 确定性运势事实。上下文强制采用以下层次：

```text
大限背景 → 流年主题 → 流月触发
```

同时要求模型区分“排盘事实、传统解释、现实建议”，禁止把流月趋势写成一定发生的工作、感情、财务或健康事件。

## 7. 测试与验收

新增 `npm run test:monthly-transits`，覆盖：

- 2026-02-16 与 2026-02-17 的农历年界；
- 2026-03-18 与 2026-03-19 的农历月界；
- 同一流月不同观察日生成完全相同快照；
- 同月缓存复用、跨月新建记录；
- 十二宫、四化、流曜和三方四正完整性；
- 流月事实进入 AI 上下文及上下文清单；
- 不存在日期的输入校验。

年度回归测试同步通过，保证 M1-2 没有改变年度快照与年度报告缓存行为。浏览器验收已验证年度 / 流月切换、正月到二月边界导航和页面无控制台错误。

## 8. 当前限制与下一步

M1-2 已具备单个流月的确定性计算、展示、缓存和追问能力，尚未包括：

- 全年十二流月横向时间轴；
- 两个重点流月的并排对比；
- 独立的流月总结报告；
- 流日确定性快照；
- 将现实人生事件精确挂到流月或流日。

下一阶段建议进入 M1-3 流日确定性排盘，先明确换日和时辰边界，再实现按需计算、缓存和日记式观察；全年流月时间轴与对比可作为 M1-2.1 的页面增强并入后续迭代。
