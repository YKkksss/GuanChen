# M4-1 双命盘持久化实施说明

> 完成日期：2026-08-15  
> 状态：已完成  
> 范围：双命盘会话、关系背景、合盘历史、刷新恢复和删除级联

## 1. 本阶段达成的效果

合盘不再是一次性页面。用户创建合盘时，系统先生成甲乙双方命盘，再把以下内容作为同一条 `heming` 会话写入本地 SQLite：

- 甲方出生信息和命盘快照；
- 乙方出生信息和命盘快照；
- 六类关系之一；
- 双方在该关系中的角色；
- 用户填写的主要现实关注；
- 后续可以继续补充的已确认现实事实。

创建成功后进入 `/heming/[conversationId]`。刷新页面、退出后重新进入或从左侧合盘历史点击记录，都会从数据库恢复双方命盘和关系背景。

## 2. 数据库变更

SQLite schema 版本升级为 V7。V1 已预留双命盘字段，V7 补充关系字段和列表索引：

| 字段 | 作用 |
| --- | --- |
| `birth_info_a_json` | 甲方出生信息 |
| `birth_info_b_json` | 乙方出生信息 |
| `chart_snapshot_a_json` | 甲方创建当时的命盘快照 |
| `chart_snapshot_b_json` | 乙方创建当时的命盘快照 |
| `relationship_type` | 情侣、商业合伙、亲子、上下级、朋友或自定义 |
| `relationship_context_json` | 双方角色、主要关注和已确认事实 |

双命盘仍放在同一条会话中，并始终使用 A/B 字段隔离。删除会话时，现有外键会级联删除该会话下的消息、记忆、上下文运行和后续报告数据。

## 3. 服务与接口

### 创建会话

`POST /api/conversations` 在 `type = heming` 时要求：

- 两张结构完整的命盘快照；
- 合法的关系类型；
- 可选的关系背景。

服务端会清洗关系背景、补齐默认角色，并按“甲方 × 乙方 · 关系类型”生成默认标题。

### 读取与管理

- `GET /api/conversations?type=heming`：只列出合盘历史；
- `GET /api/conversations/[id]`：恢复双命盘和关系背景；
- `PATCH /api/conversations/[id]`：重命名或归档；
- `DELETE /api/conversations/[id]`：删除合盘及其从属数据。

### AI 分析入口

`POST /api/heming` 改为接收 `conversationId`，服务端从 SQLite 读取双命盘，不再相信浏览器重复提交的命盘内容。关系类型、双方角色和主要关注也会进入本次提示上下文。

## 4. 页面交互

- `/heming` 用于选择关系类型、填写现实关注和双方出生信息；
- 创建按钮改为“创建并保存合盘”；
- `/heming/[id]` 展示已保存的双方摘要和关系背景；
- 左侧合盘历史支持收缩、打开、重命名和删除；
- 单盘历史与合盘历史按会话类型严格隔离；
- 当前合盘删除后返回 `/heming`，不会误跳到单盘页面。

## 5. 验证结果

自动化测试覆盖：

- 创建和读取双命盘会话；
- 未知时辰标记的保存与恢复；
- 关系类型、角色、主要关注和确认事实恢复；
- 单盘字段与双盘字段隔离；
- `chart` / `heming` 历史列表隔离；
- 重命名；
- 删除消息级联；
- V7 迁移存在性。

同时完成了生产构建和端口 30001 的真实接口回归：创建临时合盘、读取详情、读取历史、访问动态页面及删除临时记录均成功。

## 6. 本阶段边界

M4-1 只负责可靠保存和恢复“合盘资料”。当前即时 AI 输出仍是临时流式结果，刷新后不会恢复；这不是数据丢失缺陷，而是按实施顺序留给 M4-3 的合盘消息持久化与上下文工作台。

下一阶段 M4-2 将先实现可测试的双盘事实提取、条件执行、规则优先级、冲突裁决、证据清单和分维度结果。规则引擎完成后，M4-3 再把它接入持久化聊天和上下文管理。
