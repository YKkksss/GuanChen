# M3-2 报告版本差异比较实施说明

> 状态：已完成
>
> 日期：2026-08-30
>
> 数据库：SQLite v43

## 1. 阶段目标

M3-2 把“报告有多个历史版本”升级为“用户能够理解两个版本为什么不同”。专题、合盘、年度和校时四类正式报告现在都能选择两个已完成版本，并从以下三个层次进行比较：

1. 事实依据是否变化；
2. 报告文字表达是否变化；
3. 规则引擎、提示词模板、模型和 Token 等生成元数据是否变化。

系统不会只把两篇长文并排展示后让用户自己寻找差异，而是先按章节和证据标识做结构化归一，再给出明确的变化分类。

## 2. 用户可见效果

### 2.1 统一入口

以下页面在至少存在两个已完成版本时显示“版本对比”按钮：

- 单人命盘专题报告详情；
- 合盘关系报告详情；
- 年度总结报告；
- 出生时辰校时报告详情。

对比面板默认选择当前版本和它之前最近的已完成版本。用户可以重新选择基准版本与目标版本，失败或仍在生成的版本不会进入选择列表。

### 2.2 对比结果

结果包含：

- 总体判断：内容一致、仅文字表达变化、事实依据变化、仅生成配置变化；
- 变化章节数量；
- 依据变化章节数量；
- 生成元数据变化数量；
- 核心摘要左右对照；
- 每个变化章节的基准文本和目标文本；
- 新增、移除或事实内容变化的结构化依据；
- 新增和移除的行动建议、待观察事项。

### 2.3 变化分类规则

每个章节按如下规则分类：

- `unchanged`：文字和依据均一致；
- `expression_changed`：引用依据一致，仅文字变化；
- `evidence_changed`：文字一致，但结构化依据变化；
- `evidence_and_expression_changed`：依据和文字同时变化；
- `added`：目标版本新增章节；
- `removed`：目标版本移除章节。

总体判断优先级为：事实依据变化 > 文字表达变化 > 生成元数据变化 > 完全一致。这样可以防止模型措辞变化被误判为命盘事实变化。

## 3. 年度报告版本化改造

年度报告原来在同一条 `transit_reports` 记录上覆盖正文，无法恢复重新生成之前的内容。SQLite v43 新增 `transit_report_versions`，将年度报告改为与其他正式报告一致的不可变版本模式：

1. 首次生成创建 v1；
2. 手动重新生成创建递增版本；
3. 新版本生成期间继续展示旧的有效正文；
4. 新版本完成后才切换 `active_version_id`；
5. 新版本失败时恢复旧的有效版本；
6. 旧版本可以单独查看、对比和导出 PDF；
7. 删除会话时通过外键级联删除全部年度版本。

旧数据库升级时，每条已有年度报告会自动迁移为一个 `legacy_migration` 版本，不会丢失已有正文。

## 4. 生成来源审计

SQLite v43 同时为专题/合盘的 `report_versions` 和校时的 `rectification_report_versions` 增加：

- `generation_reason`：本版本的生成原因；
- `base_version_id`：本版本生成时所基于的上一个有效版本。

当前支持的生成原因：

- `initial_generation`：首次生成；
- `manual_regenerate`：用户手动重新生成；
- `source_changed`：事实依据或评估结果变化；
- `template_upgraded`：模板升级；
- `legacy_migration`：旧数据迁移。

报告详情页会展示当前版本的生成原因、提示词模板、供应商和模型；版本对比接口也会比较这些字段。

## 5. 统一差异引擎

`lib/report-comparisons/service.ts` 先把四类报告转换成统一内部结构：

- 报告标题和版本信息；
- 生成元数据；
- 摘要；
- 章节列表；
- 结构化依据；
- 行动建议；
- 待观察事项。

专题与合盘读取 `report_versions` 和 `report_evidence`；校时读取 `rectification_report_versions` 和 `rectification_report_evidence`；年度报告读取 `transit_report_versions`，并把对应的确定性年度运限快照作为权威事实依据。

依据使用 `sectionKey + evidenceKey` 作为稳定身份，再对事实对象进行键排序后的稳定序列化比较。因此对象字段顺序不同不会制造虚假差异，真正的宫位、星曜、规则命中、评估版本或运限快照变化才会被识别为事实变化。

## 6. API

新增只读接口：

```text
GET /api/report-comparisons
  ?sourceKind=topic|heming|annual|rectification
  &reportId=<报告ID>
  &baseVersion=<基准版本号>
  &targetVersion=<目标版本号>
```

接口约束：

- 两个版本号必须不同且大于零；
- 两个版本必须属于同一报告；
- 报告类型必须与实际来源一致；
- 只有已完成且存在正文的版本可以对比；
- 接口只读取本地数据，不调用 AI，不产生额外 Token 成本。

年度报告原接口增加可选 `version` 查询参数，并在响应中返回版本列表。原有不传版本的调用继续返回当前有效版本。

## 7. PDF 兼容

年度 PDF 导出现在接受版本号，并使用年度版本 ID 作为导出来源版本：

- 同一年度不同历史版本分别缓存 PDF；
- 旧版本可以独立下载；
- 当前版本的既有导出行为保持兼容；
- 来源版本、内容指纹和渲染器版本仍共同决定缓存复用。

## 8. 失败与兼容策略

- 生成失败的版本保留审计记录，但不会成为当前有效版本；
- 对比接口拒绝失败或生成中的版本；
- 年度版本迁移保留旧正文、模型、Token 和完成时间；
- 旧的年度数据库访问函数保留兼容包装，现有调用不会立即失效；
- 对比面板属于打印控制区，不会进入浏览器打印或 PDF 正文。

## 9. 验收覆盖

专项测试覆盖：

- 相同依据、不同文字被识别为“仅文字表达变化”；
- 相同证据 ID、不同事实内容被识别为“事实依据变化”；
- 规则引擎和生成元数据差异；
- `generation_reason` 和 `base_version_id` 审计链；
- 年度报告 v1/v2 不可变保存和当前版本切换；
- 年度新版本生成期间保留旧正文；
- 指定年度历史版本导出 PDF；
- 对比 API 返回结构化结果；
- SQLite v43 迁移与会话删除后的级联清理。

## 10. 当前边界

M3-2 提供只读结构化差异，不包含：

- 字符级红绿删除线算法；
- 用户手工合并两个报告版本；
- 报告正文人工编辑与批注；
- 版本确认、锁定或签名；
- 云端协作审阅。

下一步回到产品路线图，评估报告确认、备注与人工编辑层；在没有明确产品需求前，不提前引入多人协作和复杂审批流。
