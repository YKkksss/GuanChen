# 观辰 v2.0.0 版本固化规划

基准日期：2026-10-18（Asia/Shanghai）。当前开发版 `1.1.0-dev`，冻结版 `v1.0.0`，业务库 v56，全量自动回归 104/104，类型检查与生产构建通过。

> 执行顺序与阶段门以 [V2_PHASE_PLAN.md](./V2_PHASE_PLAN.md) 为准；本文日期与工期仅作历史参考，不代表承诺排期。

## 0. 结论摘要

- **推荐目标：2026-12-13 发布 `v2.0.0`。**
- **范围锁定：2026-11-22**（之后不再加新规则层）。
- **代码冻结：2026-12-04**（之后只修发布阻断问题）。
- **候选版：2026-12-05 起进入 `v2.0.0-rc`，至少 7 天只读观察。**
- v2.0 的发布理由是**统一账号、多用户隔离、可正式部署的单实例服务**，不是“术数理论开发完”。
- 下一阶段“五合去留与合化条件”**建议放入 v2.1**；若坚持纳入 v2.0，整体顺延约 3 周，目标改为 2027-01-10。

## 1. 为什么是 v2.0，而不是 1.2

v1.0.0 是单用户/可信局域网版；当前开发版已经发生以下不兼容变化：

1. 所有页面与 API 需要登录，数据按账号隔离。
2. 数据从单一 `data/ziweidoushu.sqlite` 变为 `ACCOUNT_DATA_DIR/accounts.sqlite + users/<uuid>/ziweidoushu.sqlite`。
3. 业务库从 v47 迁到 v56。
4. 部署形态从“本机工具”变为“集中后端 + HTTPS + 持久磁盘 + 备份恢复”。
5. 模块矩阵从紫微/合盘扩展到八字、合参、择日、梅花、六爻、奇门、校时、学习、案例、提醒、报告与 PDF。

这些是**使用方式与数据归属的断代变化**，按语义化版本应升 major，而不是 1.2。

## 2. 先纠正一个前提：不存在“把模块开发完”

命理规则是开放体系：五合去留之后还有合化效力、争合妒妒、动态岁运、各流派校勘；六爻还有三合墓绝反伏吟；奇门还有十干暗干长生；梅花还有外应。项目文档本身已经把“完整断法”列为长期待核。

因此 v2.0 不用“开发完”做门槛，而用**范围锁定 + 发布门槛**：

> v2.0 = 产品模块矩阵完整 + 账号与部署可用 + 已知边界写清；
> 不等于 术数理论完整，也不等于 所有流派、所有设备、真实模型质量全部验收。

## 3. v2.0 范围

### 3.1 必须包含（发布阻断）

| 领域 | 内容 |
| --- | --- |
| 账号 | 注册、登录、退出、改密、会话、管理员、账号隔离、登录限额 |
| 紫微 | 命盘、十二宫、四化、大限/流年/流月/流日、事件、运限、运势日历、运势专题、报告与版本 |
| 合盘 | 双盘、关系背景、阶段、报告、运限 |
| 八字 | 排盘、持久化、M9 条件层、论命总览、精细调候、原局作用、分方法、司令分日、月令取用入口 |
| 合参 | 本命、动态阶段、主题跨层复核 |
| 择日 | 黄历事项、区间筛选、吉时、个人化、岁运背景 |
| 独立术数 | 梅花（基础/季节/取象/占类）、六爻（基础/取用/作用路径）、奇门（基础/门星/占类） |
| 校时 | 会话、候选、事件证据、评估、报告 |
| 学习与档案 | 知识库、古籍、课程、练习、案例、提醒、月度复盘 |
| 数据 | 整库备份/恢复、加密导出、单盘迁移、PDF 导出 |
| 站点 | 登录/注册/隐私/条款、设置、数据保险箱、管理员页 |

### 3.2 明确不包含（放 v2.1 或更后）

- 五合去留、争合妒合、合化条件深化（建议 v2.1 第一项）。
- 六爻三合、墓绝、反伏吟、完整生克优先级、精确应期。
- 奇门十干克应、暗干、长生、更多占类。
- 梅花外应、后天端法、更多占类。
- 支付/会员、人物档案中心、经营咨询、Android 客户端。
- 多实例、任务队列、PostgreSQL/Redis 迁移。
- 邮件/手机找回密码、2FA、完整 AI 费用配额。
- “真实模型质量已全面合格”的宣称；v2.0 只做有预算的冒烟与抽样审阅。

### 3.3 版本边界写法

发布说明必须分栏写：

- 新增能力（相对 v1.0）
- 不兼容变化（登录、数据目录、数据库版本）
- 升级步骤（`import-legacy`、备份、停服）
- 已知限制（单进程、无找回密码、浏览器触发自动备份等）
- 下一版本（v2.1 五合去留）

## 6. 分支、标签与发布流程

1. 从 `codex/user-accounts` 盘点后切 `release/2.0`；日常开发分支继续保留。
2. 标签节奏：`v2.0.0-alpha.1`（P0 末）→ `v2.0.0-beta.1`（P1 末）→ `v2.0.0-rc.1`（P3 初）→ `v2.0.0`（P4）。
3. GitHub 建 milestone `v2.0.0`，issue 标 P0/P1/P2；P2 不阻断发布但必须记录。
4. 冻结规则：范围冻结后只接受 P0/P1 修复；代码冻结后只接受发布阻断修复，每次修复跑相关专项 + 全量。
5. 发布动作：备份 → 打标签 → GitHub Release → 部署 → 冒烟 → 观察 7 天。
6. `v1.0.0` 标签不移动；旧分支不删除；不强推。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 大量未跟踪源码/构建产物混在一起 | 移交或发布漏文件、误提交缓存 | P0 第一件事做工作区分类，先源码后产物 |
| 没有 CI/健康检查/进程守护 | 发布后故障不可见 | P1 补齐最小运维闭环 |
| 自动备份依赖浏览器 | 无人访问时不备份 | 服务器侧定时任务 + 监控 |
| 真实模型未评估 | 内容质量与成本未知 | G7 冒烟 + 抽样审阅 + 预算上限 |
| 真机/窄屏未验收 | 移动端体验回退 | P2 真机 2 台 + 四宽度 E2E |
| 范围蔓延（五合、六爻、奇门……） | 永远发不出去 | 范围冻结 + v2.1 清单 |
| 单进程限制 | 多开实例会破坏取消/锁 | 文档写清单实例，不承诺多实例 |
