# M2-5 本地档案版本化备份与安全恢复实现说明

## 1. 阶段目标

本阶段把 SQLite 从“只存在当前电脑中的运行数据”升级为可迁移、可预检、可恢复的本地档案。第一版坚持整库备份与整库替换，不做跨数据库逐表合并，避免会话、消息、事件、报告和学习记录之间的外键关系被拆散。

## 2. 备份范围

每个 `.ziweibackup` 文件包含：

1. 通过 SQLite Online Backup API 生成的一致性数据库快照，包含 WAL 中尚未落入主文件的最新提交。
2. 备份格式版本、数据库迁移版本、创建时间和各数据表记录数。
3. 数据库文件的 SHA-256 指纹和原始字节数。
4. 数据库中仍处于完成状态、且大小与 SHA-256 均匹配的 PDF 报告附件。

当前会随整库快照自然包含的业务数据包括：单盘与八字档案、聊天消息、上下文摘要与记忆、运限快照、人生事件、报告及版本、合盘、校时、课程学习、案例、提醒和月度复盘。

## 3. 备份包格式

- 文件扩展名：`.ziweibackup`
- 容器：Gzip 压缩的 JSON 信封
- 当前格式版本：`1`
- 数据库内容：Base64 编码的 SQLite 快照
- 附件内容：Base64 编码的已验证 PDF
- 最大上传体积：128 MB
- 最大解压体积：256 MB
- 最大附件数：2,000

格式版本和数据库迁移版本是两条独立的兼容性轴。格式版本决定应用能否读懂备份包，迁移版本决定当前代码能否安全运行其中的数据库。

## 4. 导入预检

用户选择备份文件后，系统只读执行以下检查，不修改当前数据：

1. Gzip 文件头、解压上限和 JSON 结构。
2. 备份类型与格式版本。
3. 数据库字节数、SHA-256 和 SQLite 文件标识。
4. SQLite `integrity_check`。
5. SQLite `foreign_key_check`。
6. 必要数据表和数据库迁移版本。
7. 清单记录数与数据库实际记录数。
8. 附件路径白名单、字节数、SHA-256 和 PDF 文件标识。
9. 备份数据库版本与当前应用数据库版本是否完全一致。

只有全部检查通过，页面才显示恢复确认入口。

## 5. 恢复与回滚流程

恢复属于整库替换，用户必须输入“覆盖本地数据”并再次确认。服务端流程如下：

1. 重新执行完整预检，不能信任浏览器此前的预检结果。
2. 将候选数据库和 PDF 写入隔离的临时位置。
3. 对当前档案再次生成完整 `.ziweibackup`，保存到 `data/backups/`。
4. 将当前 SQLite WAL 安全检查点化并关闭文件句柄。
5. 通过同目录重命名替换数据库和报告附件目录。
6. 重新打开数据库，再次执行完整性、外键和版本复核。
7. 成功后清理临时旧文件；任何一步失败则立即恢复原数据库和附件目录。

恢复前自动备份可在“本地数据保险箱”页面直接下载，再次通过预检后恢复。

## 6. 页面与接口

- 页面：`/settings/data`
- 当前数据概览：`GET /api/backups`
- 导出完整备份：`GET /api/backups/export`
- 上传只读预检：`POST /api/backups/inspect`
- 确认整库恢复：`POST /api/backups/restore`
- 下载恢复前自动备份：`GET /api/backups/automatic/:fileName`

入口已经加入新版首页模块区和东方书院功能侧栏。

## 7. 安全边界与后续演进

当前不支持：

- 将一个备份合并进已有数据库。
- 导入比当前应用更新或更旧的数据库迁移版本。
- 备份模型密钥、环境变量、运行日志或源代码。
- 云同步、自动上传或跨设备冲突合并。

后续若开发“单命盘迁移”，应采用带依赖清单的结构化 JSON，先构建 ID 映射与冲突计划，再在单个 SQLite 事务中导入；不能把任意 JSON 直接写入业务表。

## 8. 验收结果

自动化测试使用独立临时 SQLite，覆盖：

- 一致性快照生成与下载响应。
- 备份包预检接口。
- 备份后新增数据，再恢复到备份时状态。
- 恢复前自动备份可下载，且确实包含被替换前数据。
- 缺少确认文字时阻止恢复。
- 数据库指纹被篡改时阻止导入。
- 附件路径越界时阻止导入。
- 恢复后的数据库完整性和外键复核。
