# M4 合盘分析方法论与规则规范 v1

> 文档状态：M4-0 方法论定稿
>
> 实施进度（2026-08-15）：M4-1 双命盘持久化和 M4-2 规则引擎已完成，下一步进入 M4-3。
>
> 方法论版本：`heming-method-v1`
>
> 适用范围：情侣与夫妻、商业合伙、亲子、上下级、朋友和自定义双人关系
>
> 产品属性：传统文化研究与关系观察工具，不是科学测评或现实决策系统

## 1. 文档目标

本规范把项目中的合盘知识从自然语言资料转换成可以编程、测试、审计和版本化的工程规则。后续 M4 的数据库、规则引擎、上下文构建、AI 对话和专题报告都必须以本规范为准。

本规范解决以下问题：

1. 明确项目采用的紫微斗数口径，防止三合派和飞星派规则混用。
2. 明确甲方、乙方和双方互动三类证据，防止事实串位。
3. 按关系类型选择不同宫位和现实上下文。
4. 将“吉凶断语”改造成有依据、有限定条件的关系观察。
5. 建立规则优先级、冲突裁决、置信度和降级机制。
6. 约束 AI 只能解释程序提供的事实和规则结果。

## 2. 产品边界

### 2.1 本模块可以做什么

- 分别生成并保存甲乙双方命盘。
- 根据关系类型提取相关宫位、星曜、本命四化和阶段数据。
- 发现双方结构上的对应、差异、共同压力和阶段同步。
- 输出互动优势、需要经营的部分、现实验证问题和沟通建议。
- 对每条重要结论提供甲方、乙方或互动证据。
- 保存合盘历史、持续对话和版本化报告。

### 2.2 本模块不能做什么

- 不能证明两个人客观上是否适合。
- 不能预测某人一定背叛、离婚、伤害另一方或带来财富。
- 不能替用户决定结婚、分手、合作、投资、用人或医疗事项。
- 不能把用户没有确认的职业、收入、疾病、婚姻状态当成事实。
- 不能用单一百分制或星级制造虚假的精确度。
- 不能让模型自行补算宫位、星曜、四化或流年。

### 2.3 结果表达原则

项目不使用“好合盘/坏合盘”的二元标签，而是按维度输出：

- `supportive`：存在可以利用的支持性结构，仍需现实验证。
- `mixed`：同一结构可能同时形成协同和摩擦。
- `challenging`：存在需要主动管理的压力或边界问题。
- `observe`：发现结构对应，但不足以判断正负结果。
- `insufficient`：关键出生或现实信息不足，需要降低置信度。

## 3. 现有代码审计结论

### 3.1 可以直接复用的能力

- `lib/ziwei/algorithm.ts`：双方十二宫、星曜、本命四化、五行局和大限。
- `lib/ziwei/patterns.ts`：基于本项目流派口径的格局识别。
- `lib/transits/engine.ts`：指定年份的确定性运限快照。
- `lib/context/*`：历史消息、摘要、记忆和上下文预算。
- `lib/db/client.ts`：已经预留双命盘会话字段。
- M1 年度分析、M2 人生事件和 M3 报告版本能力。

### 3.2 不能直接作为正式规则使用的内容

`lib/ziwei/heming-knowledge.ts` 是早期资料汇编，存在以下问题：

- 同时出现三合派口径和跨盘飞化、自化等另一套方法。
- 包含部分绝对化、灾难化和性别刻板表达。
- 缺少规则条件、优先级、冲突关系和证据编号。
- 大量内容集中在婚恋，无法直接复用于其他关系。
- 来源粒度不足以支持逐条工程审计。

因此该文件从 M4-0 开始只作为待审资料，不得直接注入 AI，也不得被正式规则引擎导入。

## 4. 核心术语

### 4.1 三类分析对象

- `A`：甲方命盘事实。
- `B`：乙方命盘事实。
- `interaction`：程序根据 A、B 两组事实计算出的互动观察。

任何互动结论必须至少保留一条 A 证据、一条 B 证据和一条规则编号。不得把互动推断回写为某一方的本命事实。

### 4.2 三个分析层级

1. **个人基线层**：分别解释 A、B 的本命结构。
2. **互动映射层**：比较双方与当前关系有关的宫位和星曜结构。
3. **阶段触发层**：比较双方大限和流年是否同时激活相关主题。

阶段触发只能说明某个主题在当前时期更值得关注，不能覆盖本命基线，也不能单独判断关系结果。

### 4.3 三类信息可信度

- `high`：排盘程序直接生成、双方身份明确的稳定事实。
- `medium`：规则引擎根据多个确定性事实生成的传统解释。
- `low`：出生时间不确定、现实背景缺失或多个流派可能存在分歧。

## 5. 流派与事实口径

### 5.1 M4 v1 采用的统一口径

M4 v1 沿用项目现有三合派实现，允许使用：

- 双方独立的本命十二宫。
- 主星、辅星、吉曜、煞曜及庙旺利陷。
- 各自固定的本命四化。
- 三方四正和对宫关系。
- 空宫及程序已计算的借对宫信息。
- 各自当前大限所在宫位。
- 年度运势引擎已经计算出的流年快照。
- 用户明确确认的关系背景和人生事件。

### 5.2 M4 v1 明确禁用

- 宫干自化。
- 来因宫。
- 将甲方生年干飞入乙方命盘的跨盘飞化。
- 将乙方生年干飞入甲方命盘的跨盘飞化。
- 由 AI 自行计算或补全命盘事实。
- 把未经用户确认的聊天内容当成现实事实。
- 单一全局匹配分数或五星评级。

如果未来要支持飞星派，必须建立独立的方法论版本、规则集合和 UI 流派标识，不能静默混入 v1。

### 5.3 本命四化的使用方式

本命四化只作为各自命盘内部的固定事实：

- 可以说明甲方某颗化禄、化权、化科或化忌星落在甲方哪个宫位。
- 可以说明乙方对应事实。
- 可以比较双方在同一关系维度上的表达差异。
- 不得解释成某一方的四化“飞入”另一方宫位。

### 5.4 出生时间不确定

出生时间未知或未经确认时：

1. 命宫、身宫和十二宫映射相关结论标记为低置信度。
2. 不生成精确的宫位匹配结论。
3. 只保留在多个候选时辰中稳定出现的事实。
4. UI 必须展示“出生时间未确认”的明显提示。
5. 需要精确分析时转入 M5 时辰校正流程。

## 6. 不同关系类型的方法

### M4-V1-6.1 通用维度

所有关系都至少分析：

1. **互动与沟通方式**：双方命宫、福德宫和迁移宫。
2. **阶段与时间同步**：双方当前大限和所选年份的关系主题。

通用维度只提供观察框架。具体结论必须结合关系角色和现实背景。

### M4-V1-6.2 情侣与夫妻

#### 关系需求与伴侣期待

- A 夫妻宫与 A 命宫、福德宫先形成甲方关系基线。
- B 夫妻宫与 B 命宫、福德宫先形成乙方关系基线。
- A 夫妻宫主星与 B 命宫主星存在重合时，记录为“甲方期待与乙方特质的结构对应”。
- B 夫妻宫主星与 A 命宫主星存在重合时，记录反向对应。
- 双向同时出现时，记录为“双向结构对应”。

结构对应只能说明熟悉感或观察重点，不能自动解释为天作之合、婚姻稳定或现实适配。

#### 情绪与亲密节奏

- 重点比较双方福德宫和命宫。
- 同时出现多项传统压力信号时，输出“高压阶段需要更多调节”。
- 不得从煞曜直接推导分离、背叛、伤害、疾病或死亡。

#### 现实生活协作

- 官禄宫：工作投入和角色节奏。
- 财帛宫：资源获取和使用倾向。
- 田宅宫：居住、家庭资源和稳定需求。
- 现实结论必须结合双方确认的居住与财务安排。

### M4-V1-6.3 压力信号处理

煞曜、化忌和低亮度星曜属于传统压力观察，不是现实事件预测。

处理规则：

1. 单一压力信号不形成关系结论。
2. 同一维度至少需要两个独立事实，或一个事实加用户确认背景。
3. 压力结论使用 `challenging`，不使用“凶”“克”“破”等标签。
4. 必须同时给出可以验证的现实问题和可执行建议。
5. 健康、暴力、财务损失等高风险主题不得由合盘规则直接推断。

### M4-V1-6.4 商业合伙与上下级

#### 商业合伙

- 命宫与官禄宫：决策和工作方式。
- 财帛宫与田宅宫：资源、预算和长期积累方式。
- 交友宫与迁移宫：团队、客户和外部合作方式。
- 相似结构可能形成默契，也可能造成职责重叠，因此默认输出 `mixed`。

必须询问：计划职责、决策流程、股权方案、预算权限和退出机制。缺少这些信息时，不得输出“适合合伙”或“不适合合伙”。

#### 上下级关系

- A 固定为管理者，B 固定为协作者。
- 比较 A 的官禄宫、交友宫与 B 的命宫、官禄宫、福德宫。
- 命盘只能用于讨论反馈和协作方式，不能用于招聘、解雇、晋升或绩效决定。

### M4-V1-6.5 阶段同步

阶段同步按以下流程计算：

1. 分别计算 A、B 当前大限宫位。
2. 根据关系类型判断该宫位是否属于关系相关宫位。
3. 指定年份时，分别读取 A、B 的年度运势快照。
4. 当双方同时激活关系相关主题时，标记“共同关注度上升”。
5. 分别保存 A 的阶段证据和 B 的阶段证据。

阶段同步不等于“好时机”，阶段不同步也不等于“没有缘分”。

### M4-V1-6.6 亲子关系

- A 固定为父母或主要照顾者，B 固定为子女。
- A 重点看子女宫、命宫和福德宫。
- B 重点看父母宫、命宫和福德宫。
- 必须结合子女年龄、照顾安排和当前成长问题。
- 对未成年人使用成长性表达，不输出固定人格、职业或婚恋预言。

### M4-V1-6.7 朋友关系

- 交友宫、福德宫和命宫用于讨论信任、边界和相处节奏。
- 迁移宫和官禄宫用于讨论共同活动或目标协作。
- 不从单一巨门、煞曜或化忌推导朋友背叛或关系破裂。
- 涉及借贷、投资和共同财产时，优先给出现实合同与边界建议。

### M4-V1-6.8 自定义关系

自定义关系必须先收集：

- 关系名称。
- 甲方角色。
- 乙方角色。
- 主要分析问题。

第一版只运行通用互动和阶段维度，不自动套用夫妻、亲子或上下级规则。

## 7. 证据模型

每条证据至少包含：

```json
{
  "id": "chart_a:palace:夫妻宫:2",
  "owner": "A",
  "source": "chart_a",
  "factType": "palace_stars",
  "label": "甲方夫妻宫",
  "palace": "夫妻宫",
  "branch": "寅",
  "stars": ["天同", "太阴"],
  "confidence": "high"
}
```

互动结果示例：

```json
{
  "ruleId": "romantic-mutual-partner-archetype",
  "dimensionId": "relationship_needs",
  "level": "observe",
  "confidence": "medium",
  "evidenceIds": [
    "chart_a:palace:夫妻宫:2",
    "chart_b:palace:命宫:2",
    "chart_b:palace:夫妻宫:8",
    "chart_a:palace:命宫:8"
  ],
  "conclusion": "双方伴侣期待与对方命宫特质存在双向结构对应。"
}
```

证据要求：

- 跨盘规则必须同时引用 A、B 证据。
- `interaction` 不能脱离原始 A、B 证据单独存在。
- 用户事件只有 `confirmed_by_user = true` 才能作为现实证据。
- 所有证据保存方法论版本、规则版本和命盘引擎版本。

## 8. 规则契约

规则定义位于 `lib/heming/methodology.ts`，每条规则必须包括：

- 唯一的 kebab-case 规则编号。
- 规则版本。
- 适用关系类型。
- 所属分析维度。
- 优先级和置信度。
- 结构化触发条件。
- A、B 或 interaction 证据归属。
- 结论和建议模板。
- 方法论引用。
- 冲突规则编号。
- 是否启用。

M4 v1 支持的条件：

- `star_overlap`：两个指定宫位的指定类型星曜有交集。
- `star_category_count`：指定宫位某类星曜数量满足条件。
- `natal_sihua_present`：指定宫位存在固定本命四化。
- `palace_empty`：指定宫位是否为空宫。
- `birth_time_known`：某方出生时间是否确认。
- `stage_focus_in`：当前大限是否落在指定宫位集合。
- `confirmed_context_present`：现实上下文字段是否已确认。

条件列表中不提供自化、来因宫或跨盘飞化操作符。

## 9. 规则优先级与冲突裁决

当多条规则同时触发时，按以下顺序处理：

1. `insufficient` 信息不足规则优先降级相关结论。
2. 身份明确、证据完整的规则优先于缺少一方证据的规则。
3. 双向对应规则优先于单向对应规则。
4. 具体关系类型规则优先于通用规则。
5. 高优先级规则优先于低优先级冲突规则。
6. 本命基线和阶段触发分开输出，互不覆盖。
7. 支持性和压力性证据可以同时保留，不做简单正负抵消。

禁止把多维度结果加总成一个总分。UI 应分别展示每个维度的结论、证据和置信度。

## 10. AI 上下文与输出约束

AI 接收到的内容应按以下顺序组织：

1. 产品与安全规则。
2. 方法论版本及流派边界。
3. 关系类型和双方角色。
4. 甲方压缩命盘事实。
5. 乙方压缩命盘事实。
6. 规则引擎生成的互动结果。
7. 用户明确确认的现实背景。
8. 对话摘要和最近消息。
9. 当前问题。

AI 不得：

- 修改规则引擎结果的事实字段。
- 添加不存在的星曜、宫位或四化。
- 将甲方事实写成乙方事实。
- 将传统解释写成已经发生的现实事件。
- 输出禁用表达或单一匹配分数。

## 11. 现实上下文和隐私

- 合盘记忆默认只属于当前合盘会话。
- 不自动把乙方信息写入甲方个人长期记忆，反向同理。
- 关系状态、财务安排、健康信息等敏感内容必须由用户主动提供。
- 删除合盘会话时级联删除双命盘快照、消息、记忆、报告和上下文运行记录。
- 合盘报告导出前应再次提示其中包含双方个人信息。

## 12. 禁用表达

规则、提示词和报告必须阻止以下类型表达：

- 天生不合、必须分手、必须离婚。
- 一定会离婚、注定离婚、必然背叛。
- 克夫、克妻、生离死别。
- 天作之合、百分百匹配。
- 绝对适合创业、一定能发财。

推荐替代表达：

- “这个维度存在需要双方主动经营的差异。”
- “当前证据显示结构对应，但需要结合现实相处验证。”
- “双方阶段主题同时被激活，不代表结果必然吉或凶。”
- “出生时间或现实背景不足，本节结论置信度较低。”

## 13. 测试标准

### 13.1 配置静态校验

- 六种关系类型完整且不重复。
- 每种关系都有 A、B 两个明确角色。
- 每个关系至少包含互动方式和阶段同步两个通用维度。
- 宫位名称只能取项目十二宫常量。
- 规则编号唯一并符合 kebab-case。
- 规则维度必须属于其适用关系类型。
- 跨盘规则必须包含 A、B、interaction 三类证据归属。
- 冲突规则必须双向声明。
- 正式规则不得出现禁用表达。
- 自化、跨盘飞化和模型补算必须保持禁用。

### 13.2 M4-2 规则引擎测试

- 交换 A、B 后，对称关系规则结果保持对称，角色关系规则保持角色差异。
- 修改 A 的命盘不能改变 B 的原始事实。
- 单向对应和双向对应同时满足时只保留高优先级结果。
- 出生时间未知时相关结论自动降级。
- 相同命盘快照和方法论版本生成相同结构化结果。
- 阶段变化不修改本命基线。
- 任一重要结论都能回溯到规则编号和证据编号。

### 13.3 M4-3 端到端测试

- 创建合盘后刷新页面，双命盘、关系类型和聊天完整恢复。
- 切换关系类型后使用正确的宫位和现实上下文。
- AI 不会把甲方事实写到乙方名下。
- 删除会话后相关数据完整级联删除。
- 重新生成报告不会覆盖旧版本。
- 导出前能看到双方隐私提示。

## 14. 实施顺序

### M4-0：方法论工程化

- 本文档。
- `lib/heming/types.ts` 规则与证据契约。
- `lib/heming/methodology.ts` 关系定义和初始规则。
- `lib/heming/validator.ts` 静态校验。
