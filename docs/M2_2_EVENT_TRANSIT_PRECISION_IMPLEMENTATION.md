# M2-2 人生事件精确运限挂接实现说明

## 1. 本阶段目标

人生事件表原本允许填写年、月、日和日期范围，但关联表只能保存年度快照，导致“2018-07”和“2018-07-12”最终都只落到 2018 年。本阶段补齐这一层能力，使日期精度真正贯穿录入、计算、存储、展示、跳转和 AI 上下文。

核心原则：

- 现实事件以用户确认内容为准。
- 运限快照由确定性程序计算。
- 两者的挂接表示时间对齐，不证明命理结构导致了现实事件。
- 长区间只记录必要边界，不逐月、逐日制造海量关联。

## 2. 精度映射规则

| 事件日期精度 | 创建的关联 | 说明 |
|---|---|---|
| `year` | 1 个流年 | 保留原有年度关联能力 |
| `month` | 1 个流年 + 1 个流月 | 流月按真实农历月边界归一化 |
| `day` | 1 个流年 + 1 个流月 + 1 个流日 | 流日使用公历日期精确定位 |
| `range` | 覆盖年度 + 起止流月 + 起止流日 | 不展开区间内每个月和每一天 |
| `unknown` | 不创建关联 | 不对不确定日期强行推断 |

区间的年度关联继续使用 `starts_in`、`continues_in`、`ends_in`。起止月和起止日分别使用 `starts_in` 与 `ends_in`；如果起止边界落在同一个快照，系统去重后记录为 `occurs_in`。

## 3. 数据库迁移

SQLite 第 45 版迁移重建 `event_transit_links`：

- `level` 从仅允许 `year` 扩展为 `year`、`month`、`day`。
- 继续使用 `(event_id, level, target_date)` 唯一约束防止重复关联。
- 原有年度数据原样迁移，不丢失历史事件。
- 新索引按事件、层级和目标日期排序，便于页面稳定展示。

快照本身仍复用 `transit_snapshots`，相同命盘、日期、层级和引擎版本不会重复计算。

## 4. 服务层行为

`linkEventToTransits` 统一负责关联重建：

1. 检查事件是否已经由用户确认；未确认事件不创建正式关联。
2. 在写入事件前校验日期不能早于出生日期，也不能超过可计算上限。
3. 先生成覆盖年度，再根据日期精度补充流月和流日。
4. 使用“层级 + 快照目标日期”去重边界重合情况。
5. 事件日期修改后先删除旧关联，再一次性写入新关联。

仅填写出生当月时，系统使用出生日期作为该月的安全观察点，避免因为月份没有具体日期而误判为出生之前。

## 5. 页面与跳转

人生事件卡现在展示：

- 已挂接的流年、流月、流日数量。
- 每个可见快照的干支、虚岁、命宫落点或农历边界。
- 事件与快照的“发生、开始、持续、结束”关系。
- 点击后进入对应的年度、月度或日期分析页。

超长区间最多展示首尾年度和精确边界，其余年度折叠提示，避免卡片被大量年份撑高。

页面顶部固定显示事实边界：事件是用户确认的现实记录，运限挂接仅表示传统命理时间结构对齐，不构成因果证明。

## 6. AI 上下文边界

已确认事件进入上下文时会附带精简后的流年、流月、流日挂接日期。系统提示同时要求模型：

- 可以把事件本身当作用户确认事实。
- 不能把未确认候选、助手推断或命理解释补写为新事实。
- 不能因为时间结构与事件重合就倒因为果。
- 长区间的挂接日期只做摘要，控制上下文体积。

年份检索会统一从各级目标日期提取四位年份，因此月、日关联不会降低按年份召回事件的准确性。

## 7. 验证方式

```bash
npx tsc --noEmit
npm run test:events
npm run test:event-candidates
npm run test:monthly-transits
npm run test:daily-transits
npm run test:context
npm run build
```

重点覆盖：

- 年、月、日和区间的关联数量与层级。
- 区间起止关系和边界去重。
- 出生日期边界校验。
- 修改日期后旧关联完全替换。
- SQLite v45 迁移存在且允许三种层级。
- 候选事件确认后自动获得精确关联。
- 已确认事件上下文保留事实／解释边界。

## 8. 后续阶段

下一阶段建议进入 M2-3“事件专项 AI 回溯分析”：围绕用户主动选择的一条真实事件，组合该事件、对应运限快照和可追溯证据，生成可缓存、可重新打开的回溯报告；报告必须把“事实、结构、解释、待验证项”分栏呈现。
