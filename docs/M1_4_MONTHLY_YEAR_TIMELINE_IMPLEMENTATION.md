# M1-4 全年流月时间轴与重点月份对比实现说明

## 1. 阶段结论

M1-4 已把单个流月快照扩展为可连续浏览的全年流月工作台。系统会按农历流年加载全部真实流月，并允许用户选择两个重点月份进行并排比较。

本阶段完成：

- 按农历正月初一到下一年正月初一前一日生成全年流月；
- 常规年份显示 12 个流月，闰月年份显示 13 个流月；
- 每个流月展示日期范围、干支、流月命宫和本命落宫；
- 点击时间轴月份可直接打开对应的完整流月快照；
- 支持上一流年、下一流年导航；
- 支持用户自行选择两个重点月份；
- 并排比较两个月的四化、共同重点宫位及各自独有宫位；
- 复用既有 SQLite 流月快照，不增加重复的年度聚合表；
- 明确禁止系统自动评定“最好月份”“最差月份”或输出吉凶排名。

## 2. 为什么按农历流年展开

现有紫微流月使用农历初一换月，因此全年时间轴也必须沿用同一边界。若按公历 1 月至 12 月强行切分，会产生以下问题：

- 一个公历月可能跨越两个流月；
- 公历年初通常仍属于上一农历流年；
- 闰月无法在固定十二格中正确表达；
- 单月详情与全年时间轴会出现不同口径。

所以本阶段采用：

```text
lunar-year-first-day-to-next-lunar-year-eve
```

例如农历 2026 流年：

```text
2026-02-17 正月初一
  → 12 个实际流月
  → 2027-02-05 腊月末日
```

农历 2025 年包含闰六月，因此时间轴会显示 13 个流月：六月之后保留“闰六月”，再进入七月。

## 3. 确定性聚合链路

```text
用户当前流月
  → 取得所属农历流年
  → lunar-javascript 定位本年与下一年正月初一
  → 逐月调用既有 resolveMonthlyTransitPeriod
  → 得到连续 12 或 13 个真实流月区间
  → 按需读取或创建每个月的 MonthlyTransitSnapshot
  → 提取时间轴所需的小型摘要
  → 返回 MonthlyTransitYearOverview
```

聚合接口不会重新实现第二套流月算法。宫位、四化、流曜和重点宫位全部来自 M1-2 已验证的 `MonthlyTransitSnapshot`，确保单月详情与全年时间轴结果一致。

## 4. 数据结构

### 4.1 全年概览

`MonthlyTransitYearOverview` 主要包含：

| 字段 | 作用 |
| --- | --- |
| `lunarYear` | 当前农历流年 |
| `startDate` / `endDate` | 本流年可观察的公历范围 |
| `monthCount` | 实际流月数量，值为 12 或 13 |
| `boundaryPolicy` | 固化农历流年边界 |
| `comparisonPolicy` | 固化用户选择、事实差异的比较原则 |
| `previousYearStartDate` | 上一可用流年的跳转日期 |
| `nextYearStartDate` | 下一可用流年的跳转日期 |
| `months` | 全部流月摘要 |
| `evidence` | 年界、闰月和比较规则依据 |

### 4.2 单月摘要

`MonthlyTransitYearItem` 只返回时间轴与比较所需的数据：

- 原流月快照 ID；
- 流月名称、起止日期和天数；
- 流年与流月干支；
- 流月命宫及本命落宫；
- 流月四化；
- 重点宫位及理由；
- 事业、关系、财务和健康专题宫位索引。

不返回完整十二宫明细，避免全年接口重复传输大量单月详情。用户打开具体月份时，页面仍使用原来的单月接口获取完整快照。

## 5. 缓存与性能

本阶段不增加数据库表。全年概览复用 `transit_snapshots`：

```text
conversation_id + level=month + 月初日期 + engine_version
```

首次打开某个流年时，会为该次全年浏览按需准备 12 或 13 份流月快照；再次打开同一流年时全部命中 SQLite 缓存。年度聚合结果本身是轻量派生数据，不单独持久化，避免流月算法升级后产生双重缓存失效问题。

## 6. 接口

新增：

```http
GET /api/conversations/:id/transits/months?year=2026
```

约束：

- `year` 必须是四位农历年份；
- 不得早于命主出生日期所在农历年；
- 不得超过出生年后 130 年与公历 2200 年的共同上限；
- 出生所在农历年只返回出生日期以后仍有效的流月；
- 闰月年份返回 13 个流月，不能截断为 12 个。

## 7. 页面交互

流月分析页新增“全年流月时间轴”：

1. 横向滚动展示本流年全部流月；
2. 当前流月使用强调色高亮；
3. 切换日期或流年后自动滚动到当前月份；
4. 点击月份卡片后，日期、URL、完整快照和 AI 流月上下文同步切换；
5. 用户可将任意两个流月加入 A / B 对比；
6. 选择第三个月时替换最早选择项，避免界面无限扩张；
7. 对比区提供“打开本月”，可继续进入该月详情和 AI 追问。

## 8. 比较规则与风险边界

本阶段的比较口径固定为：

```text
user-selected-factual-difference
```

系统只回答“结构有什么不同”：

- 两个月分别是哪组四化、落入哪些本命宫；
- 两个月共同出现了哪些重点宫位；
- 哪些重点宫位只出现在 A 月或 B 月；
- 两个月的流月命宫、干支和有效日期分别是什么。

系统不做：

- 自动打分；
- 吉凶排名；
- 推荐所谓最佳求职、结婚或投资月份；
- 把某个结构写成必然发生的事件。

如果未来需要行动建议，仍应由用户打开具体月份后，结合现实条件、已确认人生事件和 AI 上下文进行非绝对化讨论。

## 9. 测试与验收

新增 `npm run test:monthly-transit-year`，覆盖：

- 2026 年完整 12 流月及首尾日期；
- 2025 年闰六月和 13 流月；
- 全年相邻流月无重叠、无空档；
- 每月四化和重点宫位完整；
- 重复打开全年时间轴复用同一批快照 ID；
- 全年接口不包含 `score` 或 `rank`；
- 超出出生范围的农历流年被拒绝。

同时通过 M1 年度、流月、流日回归测试与 TypeScript 类型检查。浏览器验收已覆盖：

- 2026 年 12 月时间轴；
- 月份卡片跳转和 URL 同步；
- A / B 四化及重点宫位对比；
- 2025 年 13 月与闰六月展示；
- 页面无控制台错误。

## 10. 下一阶段

M1 的年度、流月、流日及全年流月浏览主链路已经完整。下一阶段建议进入 M2-2“人生事件与流月、流日精确挂接”：

- 年精度事件关联流年；
- 月精度事件关联流月；
- 日精度事件关联流日；
- 点击事件直接打开对应时间快照；
- 在 AI 回溯中明确区分现实事实和传统解释。

这样可以让现有时间轴从“查看运限”进一步升级为“用现实经历验证和复盘运限”。
