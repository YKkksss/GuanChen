# M2-1 聊天人生事件候选提取与用户确认实施说明

## 1. 阶段结论

M2-1 已完成“聊天原话 → AI 候选提取 → 用户核对修改 → 正式事件 → 年度关联 → 后续上下文”的完整闭环。

系统可以识别用户主动提问中明确陈述的既往人生经历，但提取结果只会进入独立候选表。用户点击“确认并写入时间轴”之前，候选不会成为正式人生事件、长期记忆、报告事实或模型上下文事实。

## 2. 核心数据边界

本阶段将数据分为三层：

```text
用户聊天原话（不可修改的来源）
  ↓ AI 结构化提取
人生事件候选（待确认／已确认／已忽略）
  ↓ 用户核对并明确确认
正式 life_events + 年度关联 + confirmed_event 记忆
```

关键约束：

- AI 只能创建候选，不能直接写入 `life_events`；
- 候选不能进入正式上下文和报告事实；
- 用户可以在确认前修改标题、类型、日期、精度、影响程度和说明；
- 忽略候选不会创建任何正式事件；
- 重复确认同一候选不会重复创建事件；
- 正式事件始终保留来源消息 ID，能够回查用户原话。

## 3. 智能提取规则

提取器版本为 `life-event-candidate-extractor-v1`。

提取前先使用本地规则判断消息是否可能包含既往事件。明显的命理问题、未来预测、愿望或计划不会调用提取模型，避免无意义消耗。

模型只允许输出严格 JSON，并受到以下限制：

- 仅提取用户当前消息中明确发生过的个人经历；
- 禁止提取助手观点、命理判断、问题假设和未来计划；
- `sourceExcerpt` 应逐字引用用户原话；
- 类型必须属于现有十类事件；
- 日期精度必须是日、月、年、范围或不详；
- 没有明确影响程度时固定使用中性值 3；
- 低于 0.6 的低置信候选直接过滤；
- 出生年份之前或当前年份之后的候选直接过滤；
- 单条消息最多保留五项并按稳定指纹去重。

来源片段未逐字对齐、日期不明确或置信度较低时，候选会显示核对提示，不会静默补成事实。

## 4. SQLite v41

新增两张表：

### `life_event_extraction_runs`

记录每条用户消息的提取执行：

- 来源会话和消息；
- 提取器版本；
- 运行、完成、跳过或失败状态；
- 候选数量和错误摘要；
- 完成时间。

同一来源消息和提取器版本唯一，包含零候选的结果也会缓存，避免刷新或重试时重复调用模型。

### `life_event_candidates`

记录候选字段、来源片段、置信度、核对提示和状态。候选状态只有：

- `pending`：等待用户核对；
- `confirmed`：用户已确认，并绑定正式事件 ID；
- `dismissed`：用户已忽略。

候选按来源消息、稳定候选键和提取器版本唯一。删除会话或来源消息会级联清理候选与执行记录。

## 5. API

新增接口：

- `GET /api/conversations/:id/event-candidates?status=pending`：读取待确认候选；
- `POST /api/conversations/:id/event-candidates`：按来源消息提取或复用候选；
- `PATCH /api/conversations/:id/event-candidates/:candidateId`：确认或忽略候选。

确认请求必须携带用户核对后的完整事件字段。服务端重新执行既有事件校验，不信任客户端或模型原值。

聊天 SSE 响应增加来源用户消息 ID 响应头，使前端能在回答结束后只针对本轮用户消息触发候选提取。

## 6. 聊天确认交互

单盘聊天面板会在普通用户问题回答完成后异步检查候选：

- 没有候选时不打扰用户；
- 有候选时在输入区上方展示来源原话和候选数量；
- “核对后保存”打开完整核对弹窗；
- 用户可以修改所有关键事件字段；
- “忽略”只关闭该候选，不写正式数据；
- 确认成功后可直接进入人生事件时间轴查看。

自动命格总览、宫位点击、四化点击等隐藏系统消息不会触发人生事件提取。合盘会话也不进入本阶段候选链，避免甲乙双方事实归属混乱。

## 7. 正式事件与年度关联

用户确认后，系统复用 M2 第一版服务：

1. 按出生年份和日期精度重新校验事件；
2. 创建 `source=conversation_extracted` 且 `confirmedByUser=true` 的正式事件；
3. 保存来源用户消息 ID；
4. 根据事件年份生成或复用年度运势快照；
5. 建立发生、开始、持续或结束年度关联；
6. 把候选标记为已确认并绑定正式事件。

时间轴会明确显示“来自聊天确认”或“手动记录”，方便用户识别来源。

## 8. 长期记忆保护

旧自动记忆提取器曾允许模型直接输出 `confirmed_event`。M2-1 已收紧：

- 自动记忆提取不再允许生成 `confirmed_event`；
- 人生事件不能改写成普通 `user_fact` 绕过确认；
- 滚动摘要不能把新聊天经历升级到 `confirmed_events`；
- 重建普通记忆时保留已有用户确认事件记忆；
- 只有候选确认服务可以写入新的 `confirmed_event` 记忆。

正式事件表仍是现实事件的权威来源，记忆只是便于召回的派生入口。

## 9. 上下文注入

单盘上下文构建器会直接读取 `confirmedByUser=true` 的正式事件，并按当前问题选择最多八条：

- 明确年份匹配优先；
- 事件类型关键词匹配其次；
- 标题、说明和搜索词匹配再次；
- 同分时优先最近更新记录。

选中的事件进入独立的“用户已确认人生事件”层，并在上下文清单记录事件 ID、数量和 Token。未确认候选、已忽略候选和模型提取执行记录完全不会进入该层。

完整上下文降级时仍会保留精简的已确认事件层，避免降级路径丢失用户事实。

## 10. 幂等与异常处理

- 同一消息重复提取时复用已有执行和候选；
- 明显非事件消息缓存为 `skipped`；
- 失败执行可以重新运行，不会产生重复候选；
- 同一候选重复确认返回已创建事件；
- 候选已忽略后不能直接确认；
- 候选已确认后如需修改或删除，应在正式人生事件时间轴操作；
- 候选提取失败不会影响原本的 AI 回答和聊天保存。

## 11. 测试覆盖

专项测试 `test:event-candidates` 覆盖：

- 既往事件与未来问题的本地预筛；
- 严格 JSON 解析、低置信过滤和未来日期过滤；
- 多候选持久化与模型调用幂等；
- 确认前正式事件表、已确认记忆和事件上下文均为空；
- API 待确认列表；
- 用户修改后确认、年度关联和来源消息追溯；
- 重复确认幂等；
- 忽略候选不创建正式事件；
- 正式事件按问题和年份注入上下文；
- 普通记忆重建不删除已确认事件记忆；
- SQLite v41 迁移和会话级联删除。

## 12. 当前仍未包含

- 针对单个事件生成并缓存专项回溯报告；
- 自动把同一句话拆成多标签事件；
- 年龄轴与自然年份轴切换；
- 批量导入事件后的候选核对；
- 八字与合盘会话的事件候选提取。

按照总路线，下一阶段进入 M3 报告增强，优先实现服务端 PDF 文件导出和报告版本差异比较。事件专项回溯分析可以作为后续 M2-2 增强，在报告基础设施完善后复用同一套版本化与证据校验能力。
