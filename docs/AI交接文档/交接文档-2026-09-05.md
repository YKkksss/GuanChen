## 1. 接手前先读这一页

这是一个基于 Next.js App Router 的本地命理研究应用，已经从原开源紫微排盘项目扩展为“紫微命盘 + AI 长对话 + 运限 + 人生事件 + 报告 + 合盘 + 生时校正 + 学习 + 匿名案例 + 提醒复盘 + 八字”的综合工作台。

新接手者必须先记住以下事实：

1. 日常开发只在 `dev` 分支进行，完成开发后使用详细中文提交信息并推送到 `origin/dev`。
2. 只有用户明确提出时，才把 `dev` 合并到 `main`；当前 `main` 明显落后于 `dev`，不能把它当作最新代码。
3. 项目按本地或可信局域网单实例部署设计，没有账号、租户或用户数据隔离。
4. SQLite 是业务事实来源，默认数据库位于 `data/ziweidoushu.sqlite`；不要提交数据库、备份、报告 PDF 或 `.env.local`。
5. 项目中的出生资料、聊天、人生事件、报告、合盘和校时数据都可能是真实隐私数据，调试时不要复制到公开日志、截图、在线工具或提交记录。
6. `data/` 及可能存在的大型命盘样本、备份和导出目录不属于常规扫描范围。除非任务明确要求，否则只检查目录用途和代码接口，不遍历内容。
7. 命盘、四柱、运限、宫位关系、四化、规则命中和候选评分必须由确定性代码产生；AI 只负责解释、摘要、记忆提取和报告草稿，不能替代规则引擎。
8. 所有结果页面继续保留温馨提示：命理分析仅供传统文化学习与个人参考，不替代现实判断或专业意见。
9. 当前端口统一为 `30001`，默认开发和生产命令都监听 `0.0.0.0`，因此同一可信局域网内可能访问到共享数据。
10. 当前正在执行“全前端体验审查后的分批修复”。F01–F12 已完成，下一批为 F13 + F14 + F15，不应跳回已经结束的 M0–M9 主线重新开发。批次 B 的实现与验收见 [聊天生命周期实施记录](../F11_F12_CHAT_LIFECYCLE_IMPLEMENTATION.md)，数据库现为 v47。

## 2. 产品定位与边界

### 2.1 当前定位

产品定位不是“一次性在线算命页面”，而是：

> 以确定性排盘为基础，结合可追溯依据、长期对话记忆、人生事件、周期分析、关系研究和传统文化学习的本地个人命理研究工具。

核心价值分为四层：

- 算得出来：程序生成结构化命盘、四柱和运限事实。
- 讲得清楚：AI 把结构化事实解释为普通用户能理解的中文。
- 记得住：SQLite 保存命盘、对话、事件、报告、确认信息和派生版本。
- 可复核：重要结论尽量关联宫位、星曜、四化、岁运、规则或知识来源。

### 2.2 当前部署假设

- 单机、本地优先，也支持可信家庭或办公局域网访问。
- 暂不考虑注册、登录、权限和多租户。
- 局域网中的所有访问者共享同一套 SQLite 数据。
- 不应把 `30001` 端口映射到公网，也不应在不可信 Wi-Fi 上开放服务。
- 若未来做云端、公开网站或多用户版，需要重新设计身份、授权、隔离、审计、限流与隐私政策，不能直接沿用当前假设。

### 2.3 理论与产品安全边界

- 程序事实和 AI 解释必须分层保存，不能把 AI 推断回写成命盘事实。
- 用户在聊天中提到的人生经历不能自动升级为“已确认事件”，必须经过候选确认流程。
- 合盘必须隔离甲方、乙方和双方互动事实，禁止串人。
- 报告和 AI 回答不提供确定性的医疗、法律、投资或心理诊断结论。
- M10 的奇门、六爻、梅花、择日仍是可选独立产品线；没有方法论、确定性算法和测试前，不得仅靠提示词上线。

### 3.2 开发和提交规则

1. 开始任务前执行 `git status --short --branch`，确认仍在 `dev`。
2. 先阅读相关实施文档，再修改对应模块。
3. 尊重用户已有的未提交修改；不要用 `git reset --hard`、`git checkout --` 等命令覆盖。
4. 开发完成后运行与模块对应的专项测试、`npx tsc --noEmit`，必要时运行 `npm run build`。
5. 提交信息使用中文、开发级规范、内容尽量详细并分点说明。
6. 默认在完成每个开发阶段后自动提交并推送到 `origin/dev`。
7. 不自动合并 `main`；等用户明确要求后再执行并再次核对远程状态。

推荐提交格式：

```text
feat(模块): 一句话概括本次阶段成果

- 说明新增的用户能力和业务规则
- 说明数据结构、接口或算法变化
- 说明兼容、降级、安全或交互处理
- 说明新增测试与验证结果
```

允许的常见类型包括 `feat`、`fix`、`perf`、`refactor`、`test`、`docs` 和 `chore`。

## 4. 技术栈与运行方式

### 4.1 当前真实技术栈

以 `package.json` 为准：

| 层级 | 技术 |
|---|---|
| Web 框架 | Next.js `15.5.x`，App Router |
| UI | React `19.2.x`、TypeScript `5.x` |
| 样式 | Tailwind CSS 3 + CSS Modules + CSS Variables |
| 图标/动画 | Phosphor Icons、Framer Motion |
| 紫微排盘 | `iztro` + `lunar-javascript` + 项目内规则层 |
| 本地数据库 | `better-sqlite3`，WAL 模式 |
| AI | OpenAI Chat Completions 兼容协议，当前适配 DeepSeek 和名为 `mimo` 的兼容配置 |
| 报告导出 | PDFKit；前端另保留 html2canvas 依赖 |
| 测试 | `tsx` 运行项目内确定性测试脚本，TypeScript 编译与 Next 构建 |

注意：根目录 `README.md` 仍写着 Next.js 14 和原上游平台信息，部分描述已经过时。依赖版本、后端能力和当前产品范围应以代码、`package.json` 与本交接文档为准。

### 4.2 安装与启动

```bash
npm install
npm run dev
```

默认地址：

- 本机：`http://localhost:30001`
- 局域网：`http://<当前电脑局域网 IPv4>:30001`

其他命令：

```bash
npm run dev:local      # 仅监听 127.0.0.1:30001
npm run dev:webpack    # 不使用 Turbopack 的开发模式
npm run build          # 生产构建
npm start              # 生产服务，监听 0.0.0.0:30001
npm run start:local    # 生产服务，仅本机访问
```

不要假设交接文档写入时的开发进程在新会话中仍然存活。接手时先检查端口，再决定是否启动新进程。

## 8. SQLite 数据架构

### 8.1 初始化与运行参数

数据库入口是 `lib/db/client.ts`：

- 默认路径：`data/ziweidoushu.sqlite`。
- 可通过 `SQLITE_PATH` 覆盖，支持绝对路径和相对项目根目录路径。
- `foreign_keys = ON`。
- `journal_mode = WAL`。
- `synchronous = NORMAL`。
- `busy_timeout = 5000`。
- 当前迁移版本为 v47，迁移记录保存在 `schema_migrations`；紫微及八字消息新增原问题、重试来源和请求标识。
- 开发服务重启时，残留的紫微/八字 `streaming` 消息会标为 `failed`，错误码为 `interrupted_by_restart`。

迁移采取启动时按版本幂等执行的方式。新增表或列必须继续追加新迁移版本，不能改写已经发布的旧迁移。

备份/单命盘包沿用严格版本匹配策略：v46 旧包不能直接导入 v47，应在匹配的旧版环境恢复后再升级。已有部署数据库自动迁移；单命盘副本会重映射问答关系并清空请求标识。详见批次 B 实施记录。

## 9. AI 对话与上下文管理

完整设计见 `docs/AI_CONTEXT_MANAGEMENT_DESIGN.md`，以下是接手时必须理解的实际机制。

### 9.1 分层上下文

模型请求不是把全部历史原样拼接，而是按稳定层次组装：

1. L0：系统、安全和方法边界。
2. L1：当前命盘或四柱的权威基础事实。
3. L2：与当前问题相关的宫位、运限、规则或专题事实。
4. L3：结构化关键记忆，如用户事实、偏好、纠正和未解决问题。
5. L4：较早对话的滚动摘要。
6. L5：根据当前问题召回的旧消息片段。
7. L6：最近若干完整对话轮次。
8. L7：当前用户请求，始终完整保留。

### 9.2 预算与压缩

- 默认上下文上限约 32K Token。
- 日常输入目标约 12K Token。
- 输出预留约 2.4K Token，另有安全余量。
- 最近消息目标约 6 轮，正常预算下至少保留最近 4 轮，宽裕时通常保留 4–10 轮。
- 不是简单按固定轮数截断，而是先保护权威事实、当前问题和完整最近轮次，再分配摘要、记忆和召回预算。
- 未摘要历史超过设定阈值时执行增量滚动摘要；摘要失败时保留旧摘要并缩减最近窗口，不删除原始消息。
- FTS5 不可用时自动降级到 LIKE 子字符串检索。
- Token 计数不可用时使用保守字符估算。
- 完整构建失败时降级为“基础事实 + 最近消息 + 当前问题”。

### 9.3 记忆安全

- 允许自动提取的长期记忆类别：用户事实、用户偏好、用户纠正、未解决问题。
- AI 自己的命理推断不能保存为用户事实。
- 既往人生经历必须先成为候选，再由用户确认，不能通过 `user_fact` 绕过。
- 合盘记忆必须明确标注甲方、乙方或双方互动；归属不明就不提取。
- 原始模型 reasoning 默认不长期保存，也不回传到后续上下文。

### 9.4 流式持久化

典型流程：

```text
用户提交问题
  → 写入用户消息
  → Context Builder 组装分层上下文并记录 context_run
  → 创建 streaming 助手消息
  → 上游模型 SSE 流式返回
  → 分批更新助手消息，避免每个 Token 写一次 SQLite
  → 完成后标记 completed
  → 更新摘要、记忆、实际 Token 与上下文运行状态
```

主要入口：

- `lib/context/builder.ts`
- `lib/context/maintenance.ts`
- `lib/context/chart-context.ts`
- `lib/db/context.ts`
- `app/api/conversations/[id]/respond/route.ts`
- `app/api/bazi/conversations/[id]/respond/route.ts`
- `components/ContextMemoryPanel.tsx`

### 9.5 模型适配现状

`lib/ai/deepseek.ts` 同时提供同步和流式 Chat Completions 请求，并把上游流转换为前端 SSE。当前支持的配置分支较窄：`mimo` 使用一组兼容变量，其余供应商都落入 DeepSeek 配置。

如果后续因新模型而升级：

1. 先抽象统一 `ProviderConfig`、能力描述和参数映射。
2. 区分是否支持 `thinking`、usage、缓存 Token、流格式和最大输出字段。
3. 将 OpenAI、DeepSeek、其他兼容端分别实现，不把厂商私有参数发送给错误的端点。
4. 保持 Context Builder 和数据库结构供应商无关。
5. 使用同一批长对话、摘要、记忆、SSE 中断和错误恢复测试做回归。

### 12.3 状态、请求和长任务恢复

#### F16：接口错误反馈不一致

- 会话改名/删除、案例流程等部分操作失败时可能静默返回。
- 各模块的 loading、empty、error、retry 结构不统一。
- 建议抽象统一的请求状态组件和错误消息策略。

#### F17：人生事件候选确认流程中断

- 确认一个候选后，成功视图可能长期占据区域，剩余候选不够明显。
- 建议使用短暂成功反馈，并提供“下一个”和剩余数量。

#### F18：报告快速切换与长任务恢复不足

- 快速切换报告版本缺少请求序列保护，旧请求可能覆盖新状态。
- 长报告生成缺少更清晰的轮询、失败恢复和继续查看状态。

### 12.4 文案、隐私、知识和性能

#### F19：本地数据文案不适合局域网模式

- 页面中的“只保存在本地”容易让手机访问者理解为“保存在手机上”。
- 实际数据存储在运行项目的部署电脑，并被局域网访问者共享。
- 应统一改成“保存在部署电脑”，并区分普通备份和密码保护的加密备份。

#### F20：隐私、条款和站点元数据仍有上游旧内容

- 隐私和条款仍可能提到账号、会员、支付等当前本地版没有的能力。
- `app/layout.tsx` 的域名、站点验证和元数据仍包含旧项目口径。
- 根 README 也包含上游平台、域名、联系信息和“未包含后端 API”等已不符合本分支事实的描述。
- 公开发布前必须由产品负责人确认新品牌、主体和法律文本，再统一清理；技术开发者不能擅自给法律结论。

#### F21：无障碍和触控尺寸

- 部分辅助信息只有 8–11px，控件高度不足 44px。
- 有些可点击 `div` 缺少按钮语义、键盘支持或可访问名称。
- 部分对话框缺少完善的焦点管理。
- 建议逐页补语义按钮、`label`、ARIA、焦点圈和移动触控尺寸，并加入键盘/读屏回归。

#### F22：知识详情存在空分区

- 十四主星入口路由已恢复，但部分详情会渲染空的“其他宫位解释”。
- 应把知识状态明确分成完整、简版、待审核和未收录，不显示看似坏掉的空容器。

#### F23：古籍搜索能力和口径不足

- 结果数量可能按上限 50 截断，却看起来像完整总数。
- “全文检索”与当前实际收录的节选范围可能不一致。

#### F24：八字页面的渐进加载和体积

#### F25：工程护栏不足

## 14. 备份、恢复和隐私安全

### 14.1 已有能力

- 完整 SQLite 一致性备份。
- 恢复前格式、版本和内容预检。
- 周期自动备份和保留策略。
- 备份健康检查。
- 单命盘可移植包导出、预检和安全导入。
- 密码保护的 `.ziweibackupx` 加密备份。
- 加密使用 scrypt 派生密钥和 AES-256-GCM 认证加密。
- 密码不写入数据库；解密后复用完整内层预检。

### 14.2 操作边界

- 备份和导出可能包含真实姓名、生日、地点、事件和聊天。
- 普通备份不是脱敏文件，也不等同于加密备份。
- 恢复会替换或影响整库，是高风险操作；必须先预检并确认目标文件。
- 自动备份组件 `AutomaticBackupBootstrap` 在应用加载后会请求 `/api/backups/auto-check`，测试首页时可能产生新的自动备份文件。
- 不要为了 UI 截图随意触发恢复、删除、导入或导出。

## 15. 浏览器验证时的副作用清单

手工或自动化测试不能把所有页面都当作纯只读页面：

1. 首页挂载 `AutomaticBackupBootstrap`，可能触发自动备份检查并写入备份。
2. `/reminders` 可能在挂载时请求物化提醒实例。
3. 学习课程/课节页可能在进入后更新学习进度。
4. 某些时间轴页面在缺少报告时可能触发 AI 生成。
5. 新命盘且没有消息时，命盘详情可能自动生成 AI 总览。
6. F10 已完成：宫位点击只改变本地选择，明确点击“AI 分析此宫”才提交宫位分析。
7. 删除、恢复、授权撤销、报告重生成、案例导出都属于有业务影响的操作。

因此做页面全量扫描时应优先使用静态代码、GET 请求、已有测试数据和无副作用路由。需要执行写操作时，先明确测试目标并准备可恢复数据。

## 20. AI 交接文档维护规范

### 20.1 何时生成或更新

以下情况应生成新的交接文档：

- 即将结束一个长期开发会话。
- 即将切换到新模型或新会话。
- 完成一个大的产品里程碑。

### 20.2 文件命名

统一放在：

```text
docs/AI交接文档/交接文档-YYYY-MM-DD.md
```

同一天多次交接时优先更新当天文件，并在文末追加修订记录，避免产生难以排序的重复文件。确实需要保留多份时，再由用户决定是否增加时间后缀。

### 20.3 每次必须更新的字段

- 当前日期、分支、HEAD、远程同步状态。
- 本次完成的功能和关键文件。
- 数据库最新迁移版本。
- 已通过和未通过的测试。
- 当前未提交改动及其归属。
- 已知缺陷、风险和下一步任务。
- 新增环境变量名称，但绝不包含值。
- 是否需要用户做业务、设计、理论或发布决策。

### 20.4 禁止写入

- API Key、密码、Cookie、Token 或 `.env.local` 内容。
- 真实用户姓名、生日、地点、聊天、事件和命盘 JSON。
