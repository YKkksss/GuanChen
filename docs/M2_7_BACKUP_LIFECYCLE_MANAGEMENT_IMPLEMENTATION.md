# M2-7 本地备份生命周期管理实现说明

## 1. 阶段目标

M2-5 已经支持手动导出、预检和整库恢复，M2-6 已经支持单命盘安全迁移。本阶段补齐“用户没有主动导出时怎么办”和“已有备份还能不能用”两个长期运行问题，把备份从一次性操作升级为可持续管理的本地安全机制。

本阶段不新增 SQLite 数据表。自动备份策略和健康检查缓存保存在 `data/backups/` 的独立 JSON 文件中，因此数据库继续保持 v46，已经生成的 v46 整库备份仍然可以直接预检和恢复。

## 2. 自动备份策略

默认策略为：

- 自动备份开启。
- 每 24 小时检查一次。
- 自动保留最近 7 份周期备份。
- 首次打开应用时在后台生成第一份周期备份。

根布局挂载一个无界面的后台检查器。每个浏览器会话只发送一次到期检查，不阻塞首页渲染；服务端以互斥状态防止开发模式重复挂载或多个标签页同时创建备份。

这不是依赖常驻系统服务的 Cron。它采用“应用打开时补做”的本地部署策略：设备关机或应用未运行期间不会唤醒进程，用户下次打开应用时会立即判断是否到期并补做备份，更符合单机应用的实际运行方式。

## 3. 三类本机备份

| 类型 | 触发方式 | 自动轮换 | 用途 |
| --- | --- | --- | --- |
| 周期自动备份 | 应用打开后的到期检查 | 是，仅保留策略指定数量 | 防止忘记手动导出 |
| 手动保留备份 | 用户点击“立即保留一份” | 否 | 重要操作前主动留档 |
| 恢复前保险副本 | 执行整库恢复前 | 否 | 恢复失败或选错文件时回退 |

自动保留数量只作用于周期自动备份。系统不会因为调整周期或数量而自动删除手动保留备份、恢复前保险副本。

## 4. 备份健康检查

用户可以对任一本机备份执行完整验证。验证过程会重新读取和解包文件，并检查：

1. 文件体积、Gzip 标识和备份清单结构。
2. 数据库及附件的 SHA-256 指纹与字节数。
3. SQLite 文件标识、完整性和外键约束。
4. 必要数据表、全部表记录数清单。
5. PDF 附件路径、文件标识及数据库记录对应关系。
6. 备份数据库版本与当前应用版本是否兼容。

结果分为“待验证、健康、版本不兼容、已损坏”。健康结果与文件大小、修改时间绑定；如果用户在文件系统中替换或修改了备份文件，缓存状态自动失效并回到“待验证”。

## 5. 删除保护和路径边界

- 只允许读取、验证和删除三个受管前缀且扩展名为 `.ziweibackup` 的文件。
- 文件名必须是纯文件名，路径穿越会被拒绝。
- 下载前限制文件最大为 128 MB。
- 删除必须由用户输入“删除本地备份”，服务端再次校验确认文字。
- 自动轮换只删除明确识别为周期自动备份的旧文件。

## 6. 页面和接口

数据保险箱新增：自动备份开关、检查周期、保留数量、下次目标时间、立即本机留存、备份来源、健康状态、下载、验证和受保护删除。

接口包括：

- `POST /api/backups/auto-check`：后台到期检查。
- `PATCH /api/backups/policy`：更新自动备份策略。
- `POST /api/backups/managed`：立即创建手动保留备份。
- `POST /api/backups/managed/:fileName/verify`：执行完整健康检查。
- `DELETE /api/backups/managed/:fileName`：带确认文字删除。
- `GET /api/backups/automatic/:fileName`：下载任一受管备份，保留原路径兼容性。

## 7. 自动化验收

独立临时 SQLite 测试覆盖：

- 首次到期自动创建，周期内重复检查不重复生成。
- 周期保留数量生效，手动备份不被轮换。
- 健康备份通过完整检查。
- 文件被破坏后识别为损坏。
- 确认文字错误时拒绝删除，正确时删除文件及健康缓存。
- 策略、后台检查、手动创建、验证和删除接口均可用。

## 8. 当前边界

- 备份仍保存在当前设备，不能替代异地副本；硬盘整体损坏时，本机备份也会丢失。
- 应用未运行时不会定时唤醒，下一次打开应用时补做。
- 当前版本不读取云盘账号，也不自动上传外部服务。
- 跨设备同步、加密云备份和远端冲突合并需要作为独立阶段设计，不能把本地备份目录直接暴露到公网。
